4. 구축된 Service Account

[지시사항] 자신이 구축한 시스템의 Service-Account 기술하시오.

과제 요구사항에 맞춰 resume 네임스페이스에 service-resume ServiceAccount를 생성했습니다. Helm 템플릿의 values 설정을 통해 Deployment의 serviceAccountName에 해당 계정을 바인딩했습니다. 

# 1. ServiceAccount 존재 확인
$ kubectl -n resume get serviceaccount service-resume
NAME             SECRETS   AGE
service-resume   0         15m

# 2. Deployment에 바인딩된 ServiceAccount 확인
$ kubectl -n resume get deployment resume-web -o jsonpath='{.spec.template.spec.serviceAccountName}{"\n"}'
service-resume

5. 구축의견

[지시사항] 자신이 구축한 시스템을 소개 하시오.

로컬 PC 환경이지만 실제 운영 환경의 설계 기준을 최대한 반영해 3노드 클러스터를 구성했습니다. 가상화 단계에서는 인터넷망과 클러스터 내부 통신망을 분리해 게이트웨이 변동 시에도 노드 간 통신이 영향받지 않도록 격리했습니다.

가상 머신 OS 환경 설정부터 커널 파라미터 최적화, 쿠버네티스 패키지 설치, 노드 조인, 사설 Gitea 및 Argo CD 배포까지의 모든 인프라 셋업은 Ansible 플레이북(ansible/playbooks/site.yml)으로 모듈화하여 100% 재현 가능한 멱등성을 확보했습니다.

애플리케이션 계층은 Helm 차트로 표준화하여 패키징하고, Gitea와 Argo CD를 연동한 완전한 선언형 GitOps 파이프라인을 구축했습니다. 워크로드에는 필수 조건인 service-resume 전용 계정을 연결하고 비특권 실행 및 ConfigMap 볼륨 분리 마운트를 적용하여 프로덕션 수준의 안정성을 갖추었습니다.

6. 구축과정 및 시행착오 (실제 장애 2건)

[지시사항] 구축 과정에서 발생한 장애 또는 시행착오를 1 건 이상 기술하시오. (증상, 원인, 조치 내용을 포함)
사례 1. Hyper-V 듀얼 NIC 환경에서 Flannel CNI 노드 간 파드 통신 및 CoreDNS 단절
  • 증상: 워커 노드 파드에서 Control Plane의 CoreDNS로 질의가 타임아웃되고 파드 간 통신이 단절됨.
  • 원인: Flannel이 기본 게이트웨이가 있는 internet0(172.19.x.x)을 기본 인터페이스로 자동 선택하여 VXLAN 트래픽이 외부 가상 스위치로 누출됨.
  • 조치: kube-flannel-ds DaemonSet에 --iface=k8s0 옵션을 명시하여 클러스터 전용 고정 IP(192.168.56.0/24) 대역으로 바인딩함.
사례 2. 대용량 번들 CSS/JS ConfigMap의 256KB Kubernetes Annotation 초과 및 Argo CD 동기화 실패
  • 증상: HTML/에셋을 ConfigMap에 담을 때 metadata.annotations: Too long: must have at most 262144 bytes 에러 발생.
  • 원인: kubectl apply가 매니페스트를 last-applied-configuration 어노테이션에 직렬화하려다 256KB 한도를 초과함.
  • 조치: 1차로 Argo CD ServerSideApply=true를 적용하고, 2차로 HTML(18KB)과 CSS/JS 에셋을 별도 ConfigMap으로 쪼개어 Deployment에서 subPath 볼륨 마운트로 병합 주입함.
